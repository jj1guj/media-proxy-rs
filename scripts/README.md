# ベンチマーク実行手順

## 必要環境

- Linux
- Bash 5以上
- curl
- awk
- jq
- GNU coreutils
- ss（iproute2）
- busybox（httpdを含むもの）
- flock（util-linux）
- GNU findutils（find、xargs）

以下はリポジトリルートで実行する。

## 1. リクエスト一覧の作成

```bash
bash scripts/extract-requests.sh log_20261014.txt requests.tsv
bash scripts/prepare-dataset.sh requests.tsv ../media-proxy-rs-bench/dataset
```

ログからURL・パス・変換条件を抽出し、順序と重複を保持する。
HTTP(S)以外のURLは警告して除外する。
重複URLを除いた一覧から等間隔に選び、保存成功数が1,000件になるまで取得する。
失敗分は未選択のURLから元の出現順で補充する。候補を使い切っても不足する場合はエラーにする。
各URLの最初のリクエストのパス・変換条件を使用する。末尾の引数でURL数を変更できる。
動画なども画像と同様に保存する。取得失敗・空の本文・Content-Typeの欠落や不正は`excluded.tsv`に記録して除外し、成功分で固定する。
HTTP 200でもcurlがタイムアウトした場合は、本文が不完全な可能性があるため使用しない。
HTTP Content-Typeも保存する。データセットは作り直さず、比較する実装間で共有する。
中断後は、同じ入力・保存先・URL数で準備コマンドを再実行する。
保存済みの成功分はサイズとハッシュを確認して再利用し、不足分だけ取得する。
再取得でデータセットが変わった場合は、改善前・改善後の両方を計測し直す。

同じ取得先は同時1件・完了後1秒以上空け、異なるホスト間はCPUスレッド数まで並列取得する。
429は`Retry-After`をホストの待機期限として保存する（未指定・不正なら60秒）。
待機期限まで1秒を超えるホストは取得を保留し、別のURLで補充する。
1ファイル32MiB・60秒を上限とする。

## 2. 画像の配信

別ターミナルで起動し、計測中は動かしておく。

```bash
bash scripts/serve-dataset.sh ../media-proxy-rs-bench/dataset \
  2> ../media-proxy-rs-bench/origin.log
```

## 3. 計測

別ターミナルでサーバーを起動する。

```bash
MEDIA_PROXY_ALLOWED_NETWORKS=127.0.0.0/8 cargo run
```

```bash
bash scripts/benchmark.sh ../media-proxy-rs-bench/dataset/requests.tsv \
  http://127.0.0.1:12766 300 results
```

引数: `入力TSV 接続先 送信秒数 出力先 [同時数上限]`

負荷は49 RPS（約20.4ms間隔）で固定。
2026-10-25に `192.168.1.6:9090` の直近15日間を5秒刻みで調査し、
`sum(rate(media_proxy_requests_total{job="media-proxy-rs"}[1m]))` の
最大48.032 RPS（2026-10-11 00:35:10 JST）を切り上げた値。

同時数上限は既定1519（49 RPS × タイムアウト30秒＋余裕1秒分）。
入力を先頭から繰り返し、固定間隔で送信する。
接続先はローカルHTTPのみ。タイムアウトは30秒で、リトライはしない。
既存の出力先は上書きしない。

1,000件なら約20.4秒で一巡し、300秒で約14.7周する。
件数はキャッシュ容量や画像サイズにより調整する。1,000件すべてがキャッシュに入るとは限らない。
保存件数と元画像の合計サイズは`dataset.json`に記録する。
各実装の計測前にサーバーを再起動し、永続キャッシュがある場合も同じ初期状態に揃える。
初回と後続周回を`cycles.tsv`で比較し、配信側の`origin.log`で再取得も確認できる。
ただし再取得の減少にはキャッシュ以外に同時取得の集約も含まれ、厳密なヒット率ではない。

## 4. 結果の比較

同じ入力TSV・送信秒数・同時数上限・実行環境で取得した2つの結果を指定する。

```bash
bash scripts/compare-results.sh results-a results-b > comparison.tsv
```

送信遅延だけが基準を超えた結果を参考比較する場合は、`--allow-sender-lag`を指定する。
警告は標準エラーに出力する。未送信・件数不足・実行条件の不一致は許可しない。

```bash
bash scripts/compare-results.sh --allow-sender-lag results-a results-b > comparison.tsv
```

## 計測結果

| 出力 | 内容 |
| --- | --- |
| `summary.json` | スループット、エラー率、CPU・RSS、レイテンシ・TTFBの平均/p50/p95/p99/最大 |
| `requests.tsv` | リクエストごとのステータス、curl終了コード、応答サイズ、時間、送信遅延 |
| `cycles.tsv` | 入力一巡ごとの成功件数・エラー件数・成功応答時間 |
| `resources.tsv` | 約200ms間隔のサーバーCPU・RSS |
| `config.json` | 入力ハッシュと実行条件 |
| `errors/` | curlのエラー詳細 |

- 成功はcurl終了コード0かつHTTP 2xx。それ以外をエラーとして集計する。
- スループットは残リクエストの完了待ちを含む実測時間で計算する。
- CPUは1コア使用を100%とする。レイテンシはクライアントから見た本文受信完了までの時間。
- 未送信が発生するか、送信遅延が `max(100ms, 送信間隔)` を超えると計測を無効にし、比較を拒否する。

## 注意点

- ローカル取得先をホスト別レート制限の対象に含めない設定で比較する。既存のブロック設定も確認する。
- この試験は固定画像による処理・キャッシュの比較であり、外部通信や429対策の評価ではない。
- INFOログでは高速な正常リクエストが欠落し、画像構成に偏りが残る場合がある。
- curlは接続を再利用しない。一定間隔の送信なので本番のバーストも再現しない。
- HTTP 200の代替画像など、サーバー内部でのみ分かる失敗は検出できない。
- URLに認証情報が含まれる場合があるため、入力TSVは公開しない。

追加で確認するとよい項目: 形式・変換種別別のエラー率とp99、CPU秒/成功件数、画像品質・寸法・アニメーション保持。
